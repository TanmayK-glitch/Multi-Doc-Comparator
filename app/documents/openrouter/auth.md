# OpenRouter OAuth Authentication

## Overview

OpenRouter provides OAuth-related authentication endpoints for applications that need to obtain or exchange credentials and access tokens.

The OAuth API supports four main operations:

1. **Create an authorization code** using the PKCE flow.
2. **Exchange an authorization code for a user-controlled API key.**
3. **Retrieve OpenRouter OAuth signing keys (JWKS).**
4. **Exchange a workload identity JWT for a short-lived OpenRouter access token** using RFC 8693 token exchange.

---

## 1. Authorization Code Flow with PKCE

OpenRouter supports the OAuth authorization-code flow with **PKCE (Proof Key for Code Exchange)**.

The flow consists of two main operations:

```text
Application
    |
    | 1. Create authorization code
    v
OpenRouter
    |
    | 2. User authorizes application
    v
Callback URL
    |
    | 3. Authorization code
    v
Application
    |
    | 4. Exchange code + PKCE verifier
    v
OpenRouter
    |
    | 5. User-controlled API key
    v
Application
```

### Step 1: Create an Authorization Code

The application creates an authorization code request.

### Python example

```python
from openrouter import OpenRouter
import os

with OpenRouter(
    http_referer="<value>",
    x_open_router_title="<value>",
    x_open_router_categories="<value>",
    api_key=os.getenv("OPENROUTER_API_KEY", ""),
) as open_router:

    response = open_router.o_auth.create_auth_code(
        callback_url="https://myapp.com/auth/callback",
        code_challenge="E9Melhoa2OwvFrEMTJguCHaoeK1t8URWbuGJSstw-cM",
        code_challenge_method="S256",
        limit=100,
    )

    print(response)
```

### Parameters

| Parameter               | Required | Description                                                                                                                             |
| ----------------------- | -------- | --------------------------------------------------------------------------------------------------------------------------------------- |
| `callback_url`          | Yes      | URL where OpenRouter redirects the user after authorization. HTTPS URLs and localhost/127.0.0.1 URLs are supported for local CLI tools. |
| `code_challenge`        | No       | PKCE code challenge generated by the application.                                                                                       |
| `code_challenge_method` | No       | Method used to generate the code challenge. `S256` is the supported example.                                                            |
| `expires_at`            | No       | ISO 8601 UTC expiration timestamp for the authorization code/key.                                                                       |
| `key_label`             | No       | Custom label for the API key. Defaults to the application name if not provided.                                                         |
| `limit`                 | No       | Credit limit for the API key.                                                                                                           |
| `usage_limit_type`      | No       | Optional credit-limit reset interval, such as `monthly`.                                                                                |
| `workspace_id`          | No       | Optional workspace ID associated with the API key.                                                                                      |

## 2. Exchange Authorization Code for API Key

After the user authorizes the application, OpenRouter provides an authorization code through the callback.

The application exchanges that authorization code for a **user-controlled API key**.

### Python example

```python
from openrouter import OpenRouter
import os

with OpenRouter(
    http_referer="<value>",
    x_open_router_title="<value>",
    x_open_router_categories="<value>",
    api_key=os.getenv("OPENROUTER_API_KEY", ""),
) as open_router:

    response = open_router.o_auth.exchange_auth_code_for_api_key(
        code="auth_code_abc123def456",
        code_challenge_method="S256",
        code_verifier="dBjftJeZ4CVP-mB92K27uhbUJU1p1r_wW1gFWFOEjXk",
    )

    print(response)
```

### Parameters

| Parameter               | Required | Description                                                      |
| ----------------------- | -------- | ---------------------------------------------------------------- |
| `code`                  | Yes      | Authorization code received from the OAuth redirect.             |
| `code_challenge_method` | No       | PKCE method used during authorization.                           |
| `code_verifier`         | No       | PKCE code verifier corresponding to the original code challenge. |

The `code_verifier` is used to prove that the application completing the exchange possesses the secret generated during the initial PKCE request.

## 3. OAuth JSON Web Key Set (JWKS)

OpenRouter provides an RFC 7517 **JSON Web Key Set (JWKS)** containing the public keys used to sign OpenRouter access tokens.

JWKS can be used by systems that need to verify OpenRouter-issued access-token signatures.

### Python example

```python
from openrouter import OpenRouter
import os

with OpenRouter(
    http_referer="<value>",
    x_open_router_title="<value>",
    x_open_router_categories="<value>",
    api_key=os.getenv("OPENROUTER_API_KEY", ""),
) as open_router:

    response = open_router.o_auth.list_oauth_jwks()

    print(response)
```

### Purpose

The JWKS endpoint provides public signing keys. A service receiving an OpenRouter access token can use the appropriate public key to cryptographically verify the token signature.

## 4. Workload Identity Token Exchange

OpenRouter supports **RFC 8693 OAuth 2.0 Token Exchange** for workload identity.

An application presents a JWT issued by an identity provider trusted by the organization. OpenRouter evaluates the configured federation policy and returns a short-lived OpenRouter access token.

The resulting access token acts as the API key for the matching federation policy.

### Conceptual flow

```text
Trusted Identity Provider
        |
        | JWT / subject token
        v
Application
        |
        | RFC 8693 token exchange
        v
OpenRouter
        |
        | Federation policy evaluation
        v
Short-lived OpenRouter access token
```

### Python example

```python
from openrouter import OpenRouter
import os

with OpenRouter(
    http_referer="<value>",
    x_open_router_title="<value>",
    x_open_router_categories="<value>",
    api_key=os.getenv("OPENROUTER_API_KEY", ""),
) as open_router:

    response = open_router.o_auth.create_oauth_token(
        federation_policy_id="4b2f7d1e-8c3a-4e5f-9a6b-1c2d3e4f5a6b",
        grant_type="urn:ietf:params:oauth:grant-type:token-exchange",
        subject_token="<jwt from your identity provider>",
        subject_token_type="urn:ietf:params:oauth:token-type:jwt",
    )

    print(response)
```

### Required parameters

| Parameter              | Required | Description                                                      |
| ---------------------- | -------- | ---------------------------------------------------------------- |
| `federation_policy_id` | Yes      | Federation policy configured under OpenRouter Workload Identity. |
| `grant_type`           | Yes      | Must be `urn:ietf:params:oauth:grant-type:token-exchange`.       |
| `subject_token`        | Yes      | JWT issued by the trusted identity provider.                     |
| `subject_token_type`   | Yes      | Must be `urn:ietf:params:oauth:token-type:jwt`.                  |

### Optional parameters

| Parameter              | Description                                                                        |
| ---------------------- | ---------------------------------------------------------------------------------- |
| `requested_token_type` | When provided, must be `urn:ietf:params:oauth:token-type:access_token`.            |
| `scope`                | Optional scope. OpenRouter currently documents `inference` as the available scope. |

## 5. Application Identification Headers

OpenRouter supports optional application-identification values:

### `http_referer`

The application's URL. It is used as the primary application identifier for OpenRouter rankings and API usage tracking.

### `x_open_router_title`

The display name used for the application in OpenRouter's dashboard.

### `x_open_router_categories`

A comma-separated list of application categories, such as:

```text
cli-agent,cloud-agent
```

These values identify and categorize the application.

## 6. OAuth Error Responses

OAuth operations may return HTTP errors depending on the operation.

Common documented status codes include:

| Status Code   | Meaning / Context                           |
| ------------- | ------------------------------------------- |
| `400`         | Bad request or OAuth token-exchange error   |
| `401`         | Unauthorized request                        |
| `403`         | Forbidden request                           |
| `409`         | Conflict during authorization-code creation |
| `429`         | Rate limit / OAuth error                    |
| `500`         | Internal server error                       |
| `503`         | Service unavailable during token exchange   |
| `4XX` / `5XX` | General OpenRouter API errors               |

Applications should handle OAuth errors rather than assuming every request succeeds.

## 7. OAuth Operations Summary

| Operation                        | Purpose                                                                             |
| -------------------------------- | ----------------------------------------------------------------------------------- |
| `create_auth_code`               | Start the PKCE authorization flow and create an authorization code.                 |
| `exchange_auth_code_for_api_key` | Exchange the authorization code and PKCE verifier for a user-controlled API key.    |
| `list_oauth_jwks`                | Retrieve public keys used to verify OpenRouter access-token signatures.             |
| `create_oauth_token`             | Exchange a trusted workload-identity JWT for a short-lived OpenRouter access token. |

---

## 8. Choosing the Appropriate OAuth Mechanism

### User authorization

Use the **PKCE authorization-code flow** when an application needs authorization from a user.

```text
create_auth_code
        ↓
User authorization
        ↓
Authorization code
        ↓
exchange_auth_code_for_api_key
        ↓
User-controlled API key
```

### Workload / service identity

Use **RFC 8693 token exchange** when a workload or service has a JWT from a trusted identity provider.

```text
Identity-provider JWT
        ↓
create_oauth_token
        ↓
Short-lived OpenRouter access token
```

### Token verification

Use the **JWKS endpoint** when a system needs OpenRouter's public signing keys to verify access-token signatures.

---

## 9. Security Considerations

* Use PKCE when implementing the authorization-code flow.
* Keep the PKCE `code_verifier` secret until the authorization-code exchange is completed.
* Do not expose API keys or subject tokens in client-side source code or public repositories.
* Prefer short-lived workload-identity access tokens when using machine-to-machine authentication.
* Validate OAuth responses and handle error status codes explicitly.
* When verifying OpenRouter-issued tokens, use the OpenRouter JWKS endpoint rather than hardcoding public signing keys.
